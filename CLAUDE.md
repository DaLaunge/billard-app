# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Break & Rank" — a PWA (React + Vite) for tracking a billiards club's matches and ranking. German-language app and codebase (comments, UI strings, commit messages).

## Commands

```bash
npm run dev       # start Vite dev server (also runs the service worker in dev, see vite.config.js)
npm run build     # production build
npm run preview   # preview a production build locally
```

No lint or test tooling is configured in this repo.

Local dev needs a `.env` (copy `env.example`) with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` from the Supabase project.

## Architecture

**Single-page app, no router.** `src/App.jsx` (~550 lines) is the hub: it owns almost all state (session, player, players, matches, ratings, badges, pings, challenges, snapshots) and passes data/callbacks down to screen components in `src/components/`. There is no per-screen data fetching — `loadData()` in App.jsx re-fetches everything in one `Promise.all` after every mutation and whenever the app comes back to the foreground (at most once a minute, never on `LIVE_ENTRY_TABS` — before 2026-09-24 an open app only reloaded after its *own* mutations, so other players' results only showed up after a restart), **except three data sets that are cached per device in `localStorage` to stay inside the Supabase free plan's 5 GB egress** (it was exceeded in Sept. 2026): the rating history (`src/lib/snapshotCache.js`, only days ≥ the newest cached one are re-fetched, since `snapshot_ratings()` only ever writes `current_date`), the match list (`src/lib/matchCache.js`, delta via `matches.updated_at` + `deleted_matches` from `supabase/2026-09-24_match_delta_sync.sql`, 10 min overlap; since `supabase/2026-09-24c_matches_sync.sql` the delta comes from ONE `STABLE` RPC `matches_sync(since)` that also returns count + SHA-256 over all sorted match ids *from the same snapshot*, so concurrent reports never cause a false mismatch; a real mismatch triggers `repair()` (id list + missing rows only, not a full reload); player names are *not* cached but re-attached from the fresh players list by `attachMatchPlayers()`, so renames show up immediately) and the badge catalog (`src/lib/catalogCache.js`, re-fetched on a new `APP_VERSION`, when an awarded badge is missing from it, or after 7 days). All three fall back to a full fetch after 14 days / on a cache-version bump. **Anything that rewrites past snapshot days, or bulk-updates `matches` without going through normal `UPDATE`s (e.g. `TRUNCATE`, disabling triggers), must bump the respective `CACHE_VERSION`**, otherwise devices keep stale data for up to 14 days.

**Navigation is manual browser-history sync, not a router.** The active screen is a `tab` string in React state (`"rang"`, `"live"`, `"match"`, `"stats"`, `"profil"`, `"admin"`, `"invite"`, `"protokoll"`, `"fremdprofil"`). `navPush`/`navReplace` in App.jsx mirror every tab change into `window.history` via `pushState`/`replaceState` so the browser/device back-and-forward buttons work inside the app instead of leaving it. A `popstate` handler intercepts back/forward while `tab === "match"` and re-pushes the match state instead of letting it navigate away, so an in-progress match entry (score, run log) can't be lost to a stray back/forward click — see the long comment block above `applyNavState` in [src/App.jsx](src/App.jsx) before changing this logic.

**Business logic lives in Postgres, not in the client.** Ranking/rating calculation, badges/achievements, challenges, and pings are implemented as Postgres RPC functions (`confirm_match`, `select_badge`, `set_theme`, `update_profile`, `create_ping`, `create_challenge`, `submit_feedback`, `self_delete_account`, etc., all `SECURITY DEFINER`). The client calls `supabase.rpc(...)` and then calls `loadData()` again to pick up the recalculated state — it does not compute ranking client-side. `src/lib/achievements.js` and `src/lib/stats.js` compute *derived/display* stats client-side from already-loaded matches (streaks, high runs, etc.), not authoritative ranking.

**Database migrations are plain dated SQL files** in `supabase/`, named `YYYY-MM-DD_description.sql`. There is no `supabase/config.toml` or CLI migration history — files are applied manually (e.g. via the Supabase SQL editor), so migration order/idempotency is the author's responsibility, not the tool's.

**Supabase MCP access is read-only.** `.mcp.json` connects to the project's Supabase MCP server with `read_only=true`, and `supabase/2026-09-03_claude_readonly_role.sql` created a dedicated `supabase_read_only_user` Postgres role for it. Claude can query data for debugging but cannot write — use SQL migration files (applied by the user) for schema/data changes.

**Rating engine (`rebuild_elo()`; the formulas live in `elo_anchor_rows()` from [supabase/2026-09-24e_rebuild_elo_fast.sql](supabase/2026-09-24e_rebuild_elo_fast.sql), `rebuild_elo()` itself only writes its result since `2026-09-24g` — before that the whole thing was in [supabase/2026-09-16c_winner_stays_ties_count_in_elo.sql](supabase/2026-09-16c_winner_stays_ties_count_in_elo.sql)).** `elo_anchor_rows()` is a pure, read-only computation (one pass over all matches, all disciplines at once, state in plpgsql arrays), so it can be compared against `elo_anchors` from the read-only MCP; `2026-09-24f_rebuild_elo_messung.sql` times every function in the rebuild chain and proves old = new, rolling itself back via `RAISE EXCEPTION`. The ratings carry up to ~155 decimal places (numeric arithmetic is exact; that is where most of the CPU time goes — `power(2.0, x)` at that scale costs ~0.15 ms per call). Any change that should keep results identical must compare as `rating::text`, not with a tolerance. Elo-like, full recompute from match history (not incremental): `K=4`, start rating 500, per discipline (including a synthetic `Doppel` and `Gesamt`). Inactivity decay: no decay for the first `GRACE=30` days after a player's last match in that discipline, then exponential decay toward 500 with a `HALF=200`-day half-life. Score margin is capped at 16 points (`nf = least(n,16)`) for the delta calc; for 14/1 Endlos, negative scores are shifted up to 0 first (`sh = greatest(0, -least(score1,score2))`). Doubles matches are scored as team Elo (both partners share the same delta, based on team-average rating). `elo_anchors` stores each player/discipline's rating as of their last match — the base `snapshot_ratings()` decays from to produce daily rating history.

**Badge/achievement catalog is data-driven.** `src/lib/constants.js` exports a module-level `BADGE_INFO` map that starts empty and is populated at runtime from the `badge_catalog` table inside `loadData()`, so stateless components (e.g. `Ball.jsx`) can look up badge emoji/name/description without prop-drilling the catalog. `APP_VERSION` in the same file must be bumped on every code-changing push, **with two number spaces (user instruction 2026-09-30): WHOLE numbers (391, 392, …) only for a push from `test` to `main` that the user explicitly approved — that is what Prod runs; every push on `test` counts `<last prod number>.<minor>` (391.0, 391.1, … until the release; afterwards Prod is 392 and `test` restarts at 392.0).** It is a string, so `391.10` never collapses to `391.1`. Prod code must never carry a minor part. `report_app_version()` and the admin version list use `Math.floor(Number(APP_VERSION))` because the DB column is an integer.

**Card layout (order + column) and card visibility live on the player row (`players.card_layout`, jsonb, one entry per screen).** Each entry is an object: `{order, columns, hidden}` — `order` is ONE flat list of all the screen's cards, `columns` maps each card id to the desktop column it sits in, `hidden` is the list of cards the user switched off. **All three screens (`stats`, `live`, `profil`) use all three fields** (until 2026-09-21 only `stats` had order/columns). Because it is ONE object per screen, every write must merge (`mergeCardLayout()`) instead of replacing; since the same date that is structurally guaranteed by `useCardLayout()` ([src/lib/useCardLayout.js](src/lib/useCardLayout.js)), which holds order, columns and hidden in ONE state and always writes all three — it replaced the older split between `useHiddenCards` and StatistikScreen's own order state, where two independent writers had to merge each other's field by hand. `set_card_layout(p_screen, p_layout)` validates the screen name against a hard list, so a new screen with cards needs a migration too (see `supabase/2026-09-21_card_visibility.sql`). `reset_card_layout()` drops the whole entry, which is why the profile's "Zurücksetzen" button resets order, columns and visibility together (`clearLocal()` in `useCardLayout` keeps the local state in sync with that).

**Where a card actually ends up is decided in exactly one place per screen: a `cardsById` registry plus `cards.byColumn`.** Each screen builds the JSX of its cards into a map and then renders `byColumn.left/middle/right` into plain flex columns (`.pf-col`, `.live-col`, and on Statistik `.stat-chart-col`/`.stat-grid`); the card itself no longer knows where it lives. Every card is wrapped in a slot that carries `order` = its index in the flat order — `CardSlot.jsx` on Live/Profil, `SortableCard.jsx` (which is also the drag handle) on Statistik. **On phones the column wrappers are `display: contents`**, so all cards become direct flex children of the screen and that `order` turns them into ONE list in the saved order, regardless of column; on desktop the same value only sorts within a column and changes nothing. **But not in the raw saved order: on EVERY screen the phone shows all middle-column cards first, then all right-column cards, then (Profil only) the left side column, each group in saved order** (`PHONE_COLUMN_ORDER` in `cardLayout.js`; user feedback 2026-09-30: "Mitte zuerst, dann rechts soll ueber die gesamte App funktionieren. Es sollte alles einheitlich sein", first reported on Statistik: "if I shrink the window I expect the middle cards on top and the right ones to slide below"). The Profil identity card stays first (fixed `order: 0`). The stored `order` can interleave columns, so it is never read raw for display: `groupOrder()` produces the DISPLAYED order for every screen with more than one column, `useCardLayout` exposes it as `order`/`visibleOrder` and keeps the raw state only for saving, and drag & drop, the ▲/▼ arrows in the settings and the phone `order` all work on that one list. Each screen computes the slot `order` with `phoneSlotOrder(col, indexInColumn)` from the column the card REALLY sits in (Statistik: `middleCardIds`/`rightCardIds`, i.e. with the leaderboards deck's shared `deckCol`, not the raw `columns` field; Profil/Live: the column being rendered) — a rank of 1000 per column, so a column can never interleave with another. The Statistik `SortableContext` items are `[...middle, ...right]` on every width, because @dnd-kit animates from the order of that array. The arrows move across a column boundary by changing the card's column and placing it right behind (▲) or in front of (▼) its neighbour — a plain swap would be invisible because the grouping sorts the card straight back. Changing which column comes first is the one constant `PHONE_COLUMN_ORDER`. Consequences worth knowing: the columns must be laid out with flexbox, not grid (a `300px 1fr 300px` grid keeps the track of an emptied column and leaves exactly the wide gap this design removes — `:empty` columns are hidden and the rest share the width), and the card's own `margin-bottom` must stay 0 so the single flex `gap: var(--card-gap)` is the only spacing anywhere. Drag & drop on Statistik has to know the breakpoint (`useWideScreen()`), because @dnd-kit computes its drag preview from the on-screen neighbourhood: flat list on phones, middle-then-right on desktop.

**Which cards exist, in what default order and in which default column is a catalog in `cardLayout.js` (`CARD_SCREENS`), not something each screen defines for itself** — the settings list under Profil → "Profil bearbeiten" → "Karten" is generated from it, and `normalizeCardOrder()`/`normalizeHiddenCards()` use it to drop ids of cards that no longer exist and append ones the user has never seen. The catalog order IS the default order, so reordering the array changes what new users see. That settings list is also the only place where the order of the Live and Profil cards can be changed (Statistik additionally has drag & drop on the card itself): one row per card with ▲/▼ for the position, the name + switch for visibility and, on desktop only, a column button. Deliberately arrows and not drag & drop there: a 36px row is a poor drag target on a phone, and a slip would hit the hide switch right next to it. The row's buttons sit OUTSIDE the `<label>` — a button inside a label also toggles that label's checkbox. A card is hidden in three equivalent places: the card's own three-dot menu (`CardMenuButton`, which holds "Karte ausblenden"), the switch rows in those settings, and "Alle Karten einblenden" (`ShowAllCardsButton`) at the very bottom of each screen, above the imprint. **Hiding deliberately costs two clicks and the first one is harmless** — an earlier version had a single eye-off icon right next to the collapse chevron, and one misplaced tap made a whole card disappear while restoring it costs far more than the slip did (user feedback, 2026-09-21); the menu button therefore also sits at the FAR LEFT of the header actions, as far as possible from the collapse chevron at the card edge. Hiding from that menu also raises a toast with an **undo** that restores the exact pre-hide snapshot (not "un-hide this one card", so it can never change anything else). That is what `toast(msg, action)` in App.jsx is for — a second argument `{label, onAction}` renders a button inside the toast and stretches its lifetime to 6.5s; the 37 other call sites pass a message only and are unaffected. Toasts *with* an action let their text wrap (`.toast.with-action`), because the card name is exactly the part a single-line toast would cut off on a phone. **When adding a card to Statistik/Live/Profil, add it to `CARD_SCREENS` (with its default column) and to that screen's `cardsById`, and pass it an `onHide`** — a card missing from the catalog can be neither moved nor hidden, which is silent, not an error. Deliberately NOT orderable or hideable: the identity/profile card at the top of the left column and the tournament list (it is the entire Turniere screen). **Everything settings-, account- or support-shaped left the profile screen on 2026-09-25** and now lives behind the gear on the identity card (left of the QR icon, since 2026-09-26; before that in the profile header), i.e. inside the "Profil bearbeiten" view: "Anmeldung & Sicherheit", "Feedback" and "Meine Tickets" stopped being cards (removed from `CARD_SCREENS`, so old saved orders simply drop the ids), and "Verwaltung öffnen"/"Abmelden" moved to the end of that view. The profile itself now only shows what says something about the player. Ordering/hiding is separate from collapsing (`collapsedCards`/`openSecs`, localStorage only): collapsing is a one-device gesture, the others are lasting decisions and therefore stored on the profile.

**Several near-identical cards may share one card with tabs, without losing their individual hide/order entries ([src/components/widgets/CardDeck.jsx](src/components/widgets/CardDeck.jsx), since 2026-09-30).** This is the recipe for the screen-by-screen redesign: on these screens the padding is already tight (card 13px, header 18px, gap 12px) and the height goes into the sheer NUMBER of parallel cards, each carrying the same header, so bundling beats trimming. Done so far — Statistik: six leaderboards (Rangliste, Meiste Siege, Beste Siegquote, Aktuelle Serien, Schnellstes Tempo, Schnellstes 14/1-Tempo) → one card, phone scroll 3489px → 2616px; Profil: "Erfolge (Fortschritt)" + "Erfolge (alle)" (two cards that literally carried the SAME title) → first one card with two tabs, since 2026-10-03 ONE plain card "Erfolge" with the three nearest achievements pinned at the top (clickable: `openBadge` opens the category in the list below, scrolls to the achievement and flashes it; own profile only) — the tab buttons and the redundant "Noch x bis …" hint line were dropped (user feedback: half-redundant) — and Ratings + Rekorde + Head-to-Head + Spielgeschwindigkeit → "Meine Zahlen", phone scroll 2467px → 1270px (1925px with the full achievements tab open); Live: Duelle + Live + Planung → "Mitspieler finden", 1341px → 188px. **Live was the opposite problem** and is worth knowing about before redesigning another screen: not too full but too empty — three collapsible bars, two of which consisted almost entirely of a permanently open create form ("Ich bin bereit!", "Planung erstellen") that together filled the screen at ZERO entries. The fix there was the deck plus two more moves: the forms went behind a button so the list comes first, and with nothing entered anywhere the deck opens on the one tab that has an ACTION (`pings`, "Ich bin am Tisch") instead of an empty duel list. Its three parts also stopped being `.live-section` accordions with their own look, so the screen now speaks the same language as the other two; tab counts (`count` on a tab) replace the per-section counters, which is what keeps "is a challenge waiting for me?" answerable without switching tabs, and one collapse on the deck replaces the three per-section ones. The rules, all load-bearing: all sub-ids stay in `CARD_SCREENS` exactly as before, so the settings list, ▲/▼ ordering and the per-part switches keep working untouched; the card renders **at the slot of the FIRST still-visible sub-id** (`foldedDeck()`) and the remaining ids render nothing, which is what keeps @dnd-kit correct — its `items` must match the rendered nodes exactly, so the order and column lists are filtered through `withoutFolded()` before use. Its desktop **column** is NOT the anchor's but `deckColumn()`, the column where MOST of its parts sit (ties → catalog default): the anchor changes as parts are hidden, and layouts saved before the merge spread the parts across columns, which parked two cards in one column and left another empty. For the same reason a column change (button or drag) must move ALL the deck's ids — `cycleColumn()` therefore accepts a list. The tabs ARE the visible parts in saved order; hiding all of them removes the card. "Karte ausblenden" hides the **open tab**, not the card (hence `CardMenuButton`'s `label`) — otherwise the per-part choice from the settings would be unreachable from the card itself; the existing undo toast names the right part automatically. With one part left, `CardDeck` falls back to that part's own title (`soloTitle`, off where the collective name also reads right alone). Parts of one deck belong in the same default column and next to each other in the catalog order. **The settings list (Profil bearbeiten → Karten) shows what the screen shows, not the raw catalog (2026-09-30):** a screen entry in `CARD_SCREENS` declares its tab cards in `decks: [{id, label, ids}]` (the ONE source — `deckIds(screen, id)` feeds `LEADERBOARD_ID_LIST`, `LIVE_DECK_IDS`, `PROFIL_DECK_IDS` and `NUMBERS_DECK_IDS`), and `screenUnits(screen, order)` turns the flat order into *units* (a single card, or a whole deck at the slot of its first part). Each unit is one row with ▲/▼ (`moveUnit(ids, dir)` in `useCardLayout`: moves all parts as one contiguous block and changes the column across a column boundary like a drag), the switch and the column button. A deck row additionally carries a `Layers` icon and an `n/m` counter (this replaced the old `note` paragraph, which is gone), its parts sit indented under an accent line with their own ▲/▼ (`moveInDeck`) and switch, and the deck switch hides/shows all parts (`setDeckHidden`). **A new deck needs an entry in `decks`, otherwise it shows up as separate rows again.** The list is CSS multi-column (`columns: 2` on desktop, `break-inside: avoid` per unit) instead of the old fixed-row grid, because units differ in height. "Profil bearbeiten" also merged ball colour, profile photo and theme into ONE card "Aussehen": a single large centred ball (shows photo and chosen achievement avatar), photo actions as round icon buttons (`.icon-btn`, names in title/aria-label), the colour row, then the theme grid. The "Auto" swatch is also the way back from an achievement avatar to the own ball (`pickAuto` clears `selected_badge`); there is no separate button for that any more. **The rest of "Profil bearbeiten" follows the same rule (2026-09-30):** two columns of cards — left "Profil" + "Aussehen", right "Allgemein" (language, start page as tab-bar icons), "Dieses Gerät" (screen awake, hide tab bar, auto-update + refresh icon, notification mode as TWO switches — "Benachrichtigungen" = off/in-app, "Push" = push on top, each with its own info button — everything per device, which the card title already says) and "Konto & Hilfe" (password row, feedback row, ticket list, then shield/logout icons; `PasswordSection` and `MyFeedbackTickets` are now rows inside that card, not cards) — and the "Karten" list is a full-width section at the very BOTTOM because it is by far the biggest, followed by the footer row (reset icon + info, and the small "Meine Daten löschen" link). Full-width text buttons became `.icon-btn` icons (`.small`, `.primary` variants) with the name in `title`/`aria-label`; switch rows with an explanation use `.switch-row` (switch + optional icon button + `InfoButton`, the button must stay OUTSIDE the `<label>`). Widgets used both standalone and inside a deck (`RecordsCard`, `HeadToHeadCard`, `AchievementsProgressCard`) take an `embedded` prop that returns the body without its own `<section>`/header.

**The left column on desktop is the same on Statistik, Live and Profil, and it is ONE component ([src/components/widgets/NumbersDeck.jsx](src/components/widgets/NumbersDeck.jsx), user feedback 2026-09-30: "in der PC-Version ist auf der linken Spalte immer dieselbe Ansicht. Diese variiert nun").** After the Profil redesign it had drifted into three variants — Statistik showed identity + Rekorde + Head-to-Head (it passed `hideRatings`), Live stacked four cards, Profil showed the tabbed "Meine Zahlen" — so a user switching screens saw the column change under them. `UserPanel` (identity card + `NumbersDeck`) now builds it on Statistik and Live, and `ProfilScreen` renders the same `NumbersDeck` for its own deck; `hideRatings` is gone. Two decisions are load-bearing: (1) **which tabs exist and in what order comes from the PROFIL layout** — `numbersParts(me.card_layout.profil)` in `cardLayout.js`, with the ids in the single constant `NUMBERS_DECK_IDS` — so a tab hidden under Profil disappears from the side column on every screen, and the side column offers no hide menu of its own (`onHidePart` is only passed by Profil; hiding from Statistik would silently rewrite the Profil layout); (2) **the open tab is shared across screens** through one `localStorage` key (`numbersDeckTab`), so "Rekorde" opened on Statistik is still open on Live. The identity card is not identical on purpose: the gear ("Profil bearbeiten") only exists on Profil, because the edit view is state inside `ProfilScreen`. When adding another tab to "Meine Zahlen", touch `NUMBERS_DECK_IDS`, the `CARD_SCREENS` profil entry and `NumbersDeck`'s `bodies`/`meta` — nothing else.

**A deck card can carry a filter behind a funnel icon (`filter` prop of `CardDeck`, Statistik's "Auswahl fuer alle Statistiken", since 2026-09-30).** That selection used to be a card of its own with three rows of chips, permanently open, although it only feeds the leaderboards deck and the development chart and is rarely changed. Now a funnel in the deck's header unfolds it above the tabs (`.collapsible`, so it animates), closes via a second funnel click (there is deliberately NO OK button — changes apply instantly; only a panel that has something to reset, i.e. Letzte Matches, keeps one footer row with its reset button), and the choice itself stays where it always lived (`statGlobalDisc/-Count/-Nearby` in `localStorage`); the pill after the title always shows the discipline — its ball, or the four-ball cluster for "Alle" — plus Einzel/Doppel and the count only when they differ from the default (Beides, Top 10), so a closed panel still shows what the lists are showing. Small balls (< 18px) draw a plain white circle without a number: without it the black 8 vanished against the dark pill (user feedback 2026-09-30). The chart repeats the discipline as a pill in its time-range row — not in its title, where on a 375px phone it truncated the title. `globalFilter` left `CARD_SCREENS` (old saved orders drop the id on their own). The card's other three tools (expand all, collapse all, undo) moved into the screen header as icon buttons, because they act on every card and would have vanished together with the leaderboards deck if it is hidden. **The funnel never disappears with its card:** the funnel + panel live in [src/components/widgets/FilterFunnel.jsx](src/components/widgets/FilterFunnel.jsx) (`useFunnel`, `FunnelButton`, `FunnelPanel`), shared by `CardDeck` and `EntwicklungBlock`. If all six leaderboards are hidden, `StatistikScreen` hands the same `statFilter` object to the development chart instead (`filter={deckAnchor ? undefined : statFilter}`), because that chart is the other consumer of the selection and would otherwise be stuck on whatever discipline was last chosen. `statFilter`, `filterPill` and the `foldedDeck()` call must therefore stay BEFORE `cardsById` — the chart is built inside it and needs `deckAnchor`. **"Letzte Matches" uses the same funnel (`MatchHistoryBlock`, 2026-09-30):** player (with win/loss when a player is set), discipline, "Turniermatches ausblenden", date range and the 10/20/50/100/Alle count all sit behind it, and only the "x von y Matches" line stays visible; the closed card is ~217px shorter on a phone (719 → 502px). The header pill lists the active filters ("8B", "Odko · Siege") but collapses to "n Filter" once the text exceeds 14 characters — a long nickname otherwise truncates the title on a 375px phone, which is exactly what the chart's pill did before it moved into its time-range row. These filters are component state and reset when the screen is left, as before; only the statistics selection is persisted. **Every "how many entries" selector uses ONE scale: `LIST_COUNT_OPTIONS` = 10 / 20 / 50 / 100 / Alle, default 10 (`src/lib/constants.js`, user feedback 2026-09-30: "top 3 ist eigentlich zu wenig, wenn diese Filter so greifen").** It replaced four private scales (`[3,10,"all"]` on the leaderboards, `[3,10,20,"all"]` in Head-to-Head and in the opponent picker when creating a match, `[10,…,"all"]` in Letzte Matches). A stored choice goes through `normalizeListCount()`, so the old `statGlobalCount` value `"3"` falls back to 10 instead of leaving no chip active. New lists with a count selector must use these constants; the selector is shown only when the list is longer than the smallest step (Head-to-Head, opponent picker). **Discipline and singles/doubles are two independent filter axes (user feedback 2026-09-30: "Doppel blendet die anderen Filter fuer Disziplinen aus ... Filter pro Disziplin plus Auswahl Doppel, Einzel oder Beides").** "Doppel" used to be an entry in the discipline row because the RATING for doubles is stored as a synthetic discipline (`Doppel`), so "8 Ball in doubles" could never be chosen. Now the row is Alle + the four ball disciplines, and `ModePick` (`single`/`double`/`both`, default `both`; drawn as person glyphs — one figure, two figures, and for both the single figure in front of a dimmed pair; name only in `title`/`aria-label`) sits below it — on the statistics selection (`statGlobalMode` in `localStorage`; the old `statGlobalDisc = "Doppel"` migrates to Alle + `double`) and in Letzte Matches. `computeStats(matches, mode)` takes the mode (default `single`, so every other caller is unchanged); a doubles match counts for ALL four players with their own side's result and never when any player is a guest. **The ratings cannot follow both axes**, because the engine only keeps `Gesamt` (singles + doubles), one rating per singles discipline, and ONE `Doppel` rating for all disciplines together (`elo_anchor_rows()`): `ratingDisc` is `Doppel` in doubles mode (the discipline choice is ignored there), else the chosen discipline or `Gesamt`; the rating tab's info button says so. The development chart follows `ratingDisc`. Wins/rate/streak follow both axes exactly. A closed `.collapsible` stays in the DOM at height 0, so give it `inert` (React 18 takes `inert=""` as a string) or the keyboard walks into invisible controls — `TurniereScreen`'s form had that bug until the same day.

**Explain visually, keep prose behind info buttons, and animate anything that appears, disappears or moves (user instruction, 2026-09-30).** Three conventions that apply to every screen from here on, not just Turniere where they were introduced. (1) *Visual over textual*: a structure is drawn, not described — the four tournament formats are picked from tiles carrying small inline SVGs ([src/components/widgets/FormatGlyph.jsx](src/components/widgets/FormatGlyph.jsx)), and the same glyph marks each row of the tournament list, so the type is recognisable without reading the word. Those SVGs draw only in `currentColor` so the tile decides the colour and both themes work without a special case, and they carry no text — the name sits next to them as real, translatable text. (3) *Animate state changes*: every animation lives inside the existing `@media (prefers-reduced-motion: no-preference)` block in App.css, and the resting state must be the VISIBLE one so that switching animations off (or JS never running) can never hide content. Three reusable pieces now exist — `.reveal`/`.is-in` driven by [src/lib/useRevealOnScroll.js](src/lib/useRevealOnScroll.js) (one IntersectionObserver per list container, not per row; each row is unobserved once shown so scrolling back does not re-animate), `.collapsible`/`.collapsible-inner` which animates an UNKNOWN height via `grid-template-rows: 0fr → 1fr` (the inner element must keep `overflow:hidden` and `min-height:0`, or the row cannot shrink below its content), and the pre-existing `.tabbar-off` slide that already covers "a bar deliberately disappears". `useRevealOnScroll` takes only STABLE deps (lengths, filter values), never the array itself: a fresh array identity every render re-runs the effect, and its cleanup disconnects the observer before it can fire. It also marks anything already in view synchronously, so the first screen never waits on the observer. **A reveal list that gets UNMOUNTED and mounted again needs a re-scan too:** `MatchScreen` used to swap its whole form for `InviteScreen` via an early `return` (no longer; the QR is inline now, but the rule stands), so after coming back every card was new (`reveal`, no `is-in`) and the hook — whose deps had not changed — never re-ran: an empty list (bug 2026-10-01). Anything that can replace the observed container must be in the hook's deps (`showInvite`). **The same applies to anything that changes WHICH items are rendered, not just how many:** the opponent list is keyed by `shownKey` (the joined ids), not `opponents.length` — in doubles a selection changes the possible gain, so with "Punkte" sorting a selection swaps tiles in and out of the first N while the length stays 10, and the newly mounted tiles stayed at `opacity: 0` (bug 2026-10-01: "some opponents vanish once I click one"). **The `reveal` class must sit on an element whose `className` NEVER changes between renders:** the hook adds `is-in` straight to the DOM node, and when React re-renders a node with a different className string it rewrites the whole attribute, dropping `is-in` — the element is back at `opacity: 0` and nothing brings it back (real bug 2026-10-01: a player card in the doubles picker vanished on selection and stayed gone after deselecting). Put `reveal` on a constant wrapper (`.opp-cell` around `.opp-card`) and let the inner element carry the state classes. Table rows fade only (`tr.reveal { transform: none }`) — a transform on `<tr>` creates a containing block and WebKit has historically mishandled that. Two browser-pane testing traps, both hit for real: assigning `scrollTop` from `javascript_tool` fires NO scroll events (use `computer{action:"scroll"}`), and CSS transitions do not advance while the pane is not painting, so a just-started fade reports `opacity: 0` indefinitely and looks exactly like a broken reveal — scroll once to force a paint before believing it.

**Fun stats from the extra counters live in the Rekorde card, marked `FUN` (user request 2026-10-01).** `lib/funStats.js` (`computeFunRecords`) turns `match_counters` into record rows in the same format as the other records plus `fun: true`, which `RecordsBoard` renders as a small `FUN` pill (`.fun-tag`) after the label: Glückspilz (most flukes), Meiste Flukes in 1 Match, Runout-König, Meiste Runouts in 1 Match, Scratch-Meister, Foul-Weltmeister, Fairplay-König (fewest fouls+scratches per match, from 3 matches with counters) and Chaos-Match (most fouls+scratches of both sides). Per-device preference `matchFlyAnim` in `localStorage` (`getMatchFly()` in `uiPrefs.js`, default ON, only an explicit off is stored), switchable in TWO places: "Kugel springt in die Aufstellung" (`widgets/MatchFlySwitch.jsx`) under Profil bearbeiten → Dieses Gerät, and a "Kugel-Animation" chip in the options panel behind the arrows icon of the "Gegner" row (user could not find the profile switch). **Exactly ONE accent colour, `--accent` (`src/App.css` `:root`, written per theme by `applyTheme()` in [src/lib/themes.js](src/lib/themes.js)).** Until 2026-09-22 there were two: `--chalk` (buttons, active states) plus a hard-wired `--gold: #D6A425` that every theme carried unchanged, so a user on the red theme — or with their own accent colour under "Eigenes Thema" — still got golden highlights and secondary texts everywhere (user feedback). `--chalk`/`--chalk-deep` are now `--accent`/`--accent-deep` and `--gold` is gone. Where two highlights sit next to each other and used to be told apart by *colour*, they are now told apart by **fill level** of the same accent: `--accent` (full area, text on it is `--accent-ink`) → `--accent-mid` (second filled area beside a full one, text `--ivory`) → `--accent-soft` + `--accent-line` (tinted area / half-strength border) → plain accent text. **Don't fill an area with `--accent-deep`**: it comes from the theme and is bright enough in the yellowish presets (`Rot`: `#B48446`) that neither light nor dark text is reliably legible on it — it is a border/line colour, and `--accent-mid` (mixed against `--felt`, so its lightness drops in every theme) exists precisely for that case. Print styles use the accent darkened against black, because white paper needs it. When adding CSS, use the tokens — a raw hex is what caused this in the first place.

**Secondary controls get a surface, not an outline (`--surface-btn`, since 2026-09-25).** Ghost buttons, chips, toggles and selection tiles used to be transparent with a visible `--btn-border`; a single profile screen carried over a dozen outlines, which reads as noise and competes with the content the user wants dominant. They now sit on `--surface-btn` (= `--felt-3`, which works both on the page background `--felt` and on a card `--felt-2`) with a *transparent* 1.5px border — the border stays in the box model so nothing changes size and hover only has to colour it in. The one list of selectors in App.css under "EINHEITLICHES BUTTON-SYSTEM" is where a new control gets registered; a state class (`.active`/`.on`/`.sel`/`.selected`) wins over it by specificity and keeps its accent fill, **except where the group selector itself carries `:not()`** — `.chip-btn` needs `:not(.sel)` there, because `.chip-btn:not(.ok):not(.no)` (0,3,0) would otherwise beat `.chip-btn.sel` (0,2,0). `--btn-border` is now only for the controls that genuinely keep a border (list rows, small icon buttons) and for hover.

**Per-device display preferences live in `localStorage`, not on the player row** (`src/lib/uiPrefs.js`, plus `keepScreenAwake` in `wakeLock.js` and the update interval): what a phone needs is not what a desktop needs, so these deliberately do not sync. `hideTabbarOnScroll` (Profil → Profil bearbeiten → Bildschirm) drives `useHideTabbar()` ([src/lib/useHideTabbar.js](src/lib/useHideTabbar.js)), which hides the bottom bar while scrolling down. Two things there are load-bearing: the hook takes the scroll container as a **DOM node from `useState` (`ref={setContentEl}`), not a `useRef`** — `<main class="content">` only renders once a player is loaded, and a ref never re-runs the effect, so it would attach to nothing; and it throttles on a **timestamp, not `requestAnimationFrame`** — rAF does not run while the page isn't painted, which makes the hook untestable in a hidden browser pane and leaves an "already queued" flag stuck until the next frame. Default is off.

**PWA/service worker update handling** is in App.jsx via `useRegisterSW`, and depends on `vite.config.js` using `registerType: "prompt"` (**not** `"autoUpdate"`) with no `skipWaiting` in the `workbox` options. With `"autoUpdate"`, vite-plugin-pwa's own generated client code reloads the page unconditionally the moment a new service worker activates — it never calls `onNeedRefresh` at all in that mode (see `node_modules/vite-plugin-pwa/dist/client/build/react.js`), so no app-level deferral logic can hook in, regardless of what that callback is named or does. `"prompt"` mode instead calls `onNeedRefresh()` when an update is waiting and leaves activation to the app; without `skipWaiting`, the new worker parks in the "waiting" state until the app calls `updateServiceWorker(true)` (which sends the skip-waiting message — the actual reload then happens via vite-plugin-pwa's own "controlling" listener once the new worker takes over, not via a `window.location.reload()` call in App.jsx). **A past version of this code passed a non-existent `onNeedReload` option (the real one is `onNeedRefresh`) while still on `registerType: "autoUpdate"` — this silently produced the exact immediate-reload-with-no-deferral behavior described above, invisibly, because both mistakes independently bypass the same gate.** If updates ever start applying immediately again, check both of these first before assuming the bug is in App.jsx's own trigger logic.

Update checks are a per-device switch, `auto` (default) or `manual` (`localStorage` `updateCheckInterval`, since 2026-09-26; the old 30/60-minute and "every open" options map to `auto`). `auto` checks on start, on every return to the foreground (throttled to 2 min) and every 30 min — interval-only checks never ran on iPhones, where `setInterval` stands still while the PWA is frozen in the background. `persistNavAndUpdate` additionally reloads by itself 4 s after skip-waiting if a *different* worker became active (iOS standalone doesn't reliably deliver the `controlling` event; the "different worker" condition prevents a reload loop via trigger 4), and trigger 5 skips its `getSession()` wait (`immediate`), because iOS freezes the page before it would finish. **Trigger 6 (since 2026-09-26): an update already waiting at page load is applied right away** — a plain reload (pull-to-refresh) never activates a waiting worker, and trigger 4 usually missed it because `onNeedRefresh` arrives after the player is loaded. It asks `getRegistration()` directly and posts `SKIP_WAITING` to `reg.waiting` itself (workbox-window may not know the registration that early). Safe for `LIVE_ENTRY_TABS`: right after a page load nothing unconfirmed is in memory (the match draft is in localStorage). iOS Home-Screen PWAs have no native pull-to-refresh at all, so `usePullToRefresh()` ([src/lib/usePullToRefresh.js](src/lib/usePullToRefresh.js)) adds one there only (never in a browser or on Android): passive listeners on `<main class="content">`, blocked while `html.live-entry` is set, only from scrollTop 0 and only if the pull starts within 250 ms (Statistik's card drag activates after 300 ms). On release it runs `reg.update()`, waits for an installing worker, then reloads, so trigger 6 applies a just-published version in the same gesture. A found update is applied at one of five deliberately narrow, predictable moments (an earlier version used a more general "any screen change, or backgrounding" rule — replaced 2026-09-15 as too unpredictable to reason about, then partially reinstated 2026-09-16, see Trigger E below):
1. **Switching to one of the 4 main bottom-tab-bar destinations** (`MAIN_TABS`: `stats`, `turnier`, `live`, `profil`) — hooked into the same tab-change detection as before, but only fires when the *destination* is one of these four, not on every navigation. **Not when the tab being left is a `LIVE_ENTRY_TABS` screen** (since 2026-09-24): "Abbrechen" in match entry goes back via `history.back()` to the previous main tab, and without this exception the app reloaded right after an aborted match (user feedback: nothing should reload there). The update then waits for the next trigger.
2. **An explicit user request** — "Nach Updates suchen" in profile settings, via `requestUpdateNow()`. This applies immediately (no deferral) since the user explicitly asked for it — *except* while on a `LIVE_ENTRY_TABS` screen, where it only checks and never force-applies. That guard currently never fires (the only caller lives on `profil`); it stays as insurance for any future caller reachable mid-match. A second caller, a floating "Aktualisieren" button at the top right, was removed 2026-09-21 — pulling the page down to reload is the more intuitive gesture and already works, and the resulting page load applies a waiting update via trigger 4.
3. **Right after any `loadData()` run** (tracked via the `loadGen` counter, which — unlike `initialLoadDone` — changes on every run, not just the first). Since every successful mutation RPC is followed by `loadData()`, this is what covers "a match or tournament result was saved." Still gated on `LIVE_ENTRY_TABS` — a live Winner-Stays session calls `loadData()` after every individual game while the session tab is still `"winnerstays"`, well before the session itself ends. The effect must check that `loadGen` itself just changed (via a ref), not merely that it's non-zero — otherwise it re-fires on every unrelated dependency change (e.g. the instant an update is *detected*, regardless of any save).
4. **Right after the player is established for the first time in this page load** (the `!startTabAppliedRef.current` block below) — covers a fresh login and a resumed persisted session alike; nothing was visibly rendered yet, so it's as unnoticeable as a real transition.
5. **The tab going to the background** (`visibilitychange` → hidden) — gated on `LIVE_ENTRY_TABS` like the others. Removed in the initial 4-trigger redesign for being too unpredictable, then reinstated because triggers 1-4 rarely fire on desktop, where a single tab often stays open for hours without ever hitting a main tab, saving anything, or logging in again — unlike mobile, where closing/reopening the PWA naturally exercises trigger 4. Observed directly as "works on phone, not on PC."

**When adding a new screen that holds unconfirmed live entry across renders, add its tab to `LIVE_ENTRY_TABS`** — Claude should proactively judge whether a new screen needs this and add it, or ask if unsure, without waiting to be told.

All five persist the current navigation state (tab + ids like `tournamentId`/`winnerStaysId`/`protokollMatch`/etc.) to `sessionStorage` (`RESUME_NAV_KEY`) right before calling `updateServiceWorker(true)`, and restore it on the next mount (`resumedNav`) instead of falling back to the default start tab — otherwise the eventual reload would silently bounce a permanently-displayed screen back to the home tab. See the comment block above `MAIN_TABS`/`LIVE_ENTRY_TABS` near the top of [src/App.jsx](src/App.jsx) before changing this logic.

**Forced minimum version (`supabase/2026-09-23b_app_version_gate.sql`).** On startup and when the app returns to the foreground (throttled to 10 min) App.jsx calls `report_app_version(APP_VERSION)`, which records the version on `players.app_version`/`app_version_at` (written only on change or once a day) and returns `app_settings.min_app_version`. If `APP_VERSION` is below it, `mustUpdate` shows a blocking overlay, polls for the new SW every 30s and applies it as soon as it is waiting — bypassing triggers A–E but still never on `LIVE_ENTRY_TABS`. Only works from version 377 on (older builds don't have the check). Since `supabase/2026-10-01_app_version_full.sql` the app also sends the full string (`p_full`, column `players.app_version_full`, shown in the admin list) so minor builds like `391.25` are visible; until that migration is applied the call falls back to the old one-argument form (a 404 on the first call in the network tab is expected then). Verified 2026-10-01 with a production build and the service worker: a minor bump (391.25 → .26 → .27) is delivered both by the explicit "Jetzt nach Updates suchen" icon and by the automatic check (found, parked as waiting, applied on the next main-tab switch), and the open tab is restored. Only ever set the minimum to a version that is already deployed, otherwise every client stays locked.

**Pull-to-refresh is disabled on `LIVE_ENTRY_TABS`** (class `live-entry` on `<html>` → `overscroll-behavior-y: none`). Pulling down is deliberately the way to reload everywhere else (see trigger 2), but mid-match a slip while typing a score would reload the page and lose the whole entry.

**Unfinished match entry survives a forced reload (`src/lib/matchDraft.js`, since 2026-09-24).** Everything the app *can* prevent is prevented (no update, no pull-to-refresh on `LIVE_ENTRY_TABS`), but not the rest: the OS killing the backgrounded PWA, a second open instance applying an update (`clientsClaim` → the "controlling" reload hits this tab too), or a lost session. So `MatchScreen` writes its full state on every change (steps 1–3) to `localStorage` `matchDraft:<playerId>` — for 14/1 including the complete `StraightPoolScorer` state via its `initialState`/`onStateChange` props — and App.jsx offers "Unfertiges Match: Fortsetzen / Verwerfen" outside match entry. The draft is deleted on save (step 4), on cancel and on discard, expires after 12 h, and is never sent anywhere. **When adding state to `MatchScreen` or `StraightPoolScorer`, add it to the draft too**, or a resumed match silently loses it. Winner Stays only keeps the current game's score locally (`wsDraft:<sessionId>`, bound to the last reported `game_no`, so it is dropped once any device reports a game).

**Screen Wake Lock (`src/lib/wakeLock.js`) hangs off the same `LIVE_ENTRY_TABS` list.** While one of those screens is open, the app holds a screen wake lock so the phone doesn't lock mid-match. Two levels, deliberately: `keepAwakeDefault` in App.jsx is the persistent preference (profile → "Profil bearbeiten" → "Bildschirm", stored in `localStorage` as `keepScreenAwake`, default on — only an explicit "off" is written, so a fresh device gets the default), while `keepAwakeNow` drives the quick toggle in the match/Winner-Stays header (`widgets/KeepAwakeButton.jsx`) and is reset to the default every time a live-entry screen is *entered*, so a one-off "off" never silently becomes a second permanent setting. The browser releases the lock itself whenever the page goes to the background and does not restore it, hence the re-request on `visibilitychange`. Devices without the API (iOS before Safari 16.4) never see the button.

**Both the update-apply path and the app's initial auth check wait on `supabase.auth.getSession()`, each guarded by its own timeout (`Promise.race` against a plain `setTimeout`)** — 2s in `persistNavAndUpdate`, **15s** in the startup effect that sets `authReady`. Two real, confirmed bugs drove this: (1) reloading while a token refresh is in flight can strand a stale, already-rotated refresh token in `localStorage` (Supabase rotates on every refresh), so the next refresh attempt fails with `refresh_token_not_found` and the user gets signed out — confirmed via that exact error in the Supabase auth logs during a heavy round of reload testing; `persistNavAndUpdate` now awaits `getSession()` first so an in-flight refresh gets to finish and persist before the reload tears the page down. (2) That same `getSession()` call, if it ever hangs (e.g. a stuck internal lock), previously left `authReady` permanently `false`, so the app showed nothing but its loading screen forever on a plain browser refresh — the timeout guarantees `authReady` always resolves. Neither hang was reproduced directly (session-shared local testing made that unreliable); both fixes are defensive and safe regardless of the exact trigger. **The startup timeout started at 5s but was raised to 15s after it caused iPhone users to be bounced to the login screen on every app relaunch**: reopening a Home-Screen PWA that iOS fully terminated (swiped away, not just backgrounded) is a real cold start, and WebKit's storage engine can take measurably longer than 5s to come back up — the short timeout was firing and defaulting to "no session" before the real, valid session had even finished loading. If a similar "logged out for no reason" report comes in again, suspect this timeout being too short before suspecting actual session/storage loss.

**Notifications (`src/lib/notifications.js`, `supabase/2026-09-23_push_notifications.sql`, setup in [PUSH_ANLEITUNG.md](PUSH_ANLEITUNG.md)).** One per-device mode in localStorage (`notifyMode`: `off` / `inapp` default / `push`). Events are produced by **table triggers** (challenges, matches + match_confirmations, tournament_matches + tournaments start, winner_stays_entries, pings, plannings, replies), never in the RPCs, and all go through `notify_players()`, which writes the row to the `notifications` inbox (texts built there in de + en) and, if the recipient has a `push_subscriptions` row, calls the Edge Function `send-push` via `pg_net` (URL + secret from Vault). `inapp` polls that inbox every 30s; `push` gets pushes via `public/push-sw.js` (pulled into the generated SW through `workbox.importScripts`, which is why the dev SW is `type: "classic"`). With the app visible, the SW forwards the push as a toast instead of a system notification, except on Safari/iOS, which revokes push permission for pushes without a visible notification. `tourney_ready`/`ws_ready` don't toast because the existing "Du bist dran!" popups cover them; `off` hides those popups as well. `notify_players()` swallows its own errors on purpose: a broken notification must never roll back the match/ping that triggered it.

**Two stray root-level files, `main.jsx` and `supabase.js`, are unused legacy leftovers** — the real entry point is `src/main.jsx` (referenced by `index.html`), and the real Supabase client is `src/supabase.js` (which additionally derives `DB_REF` from the project URL). Don't edit the root copies; they aren't wired into the build.

## Known gotchas

- **CSS Grid cross-column height coupling.** When a column is built from two separate grid items stacked in two grid *rows* (as opposed to one flex column), Grid sizes each row by the tallest item across *all* columns in that row — a short/empty module next to a tall one in the neighboring column produces large, seemingly-unrelated gaps. Fix is to make each visually-stacked column its own flex container instead of relying on grid-row alignment.
- **`elo_anchors` has its own surrogate primary key** — it is not the `(player_id, discipline, anchor_at)` tuple that code elsewhere treats as its natural key. Adding a second `PRIMARY KEY` on that tuple fails with `42P16: multiple primary keys`; use a plain `UNIQUE` constraint instead (sufficient for `ON CONFLICT` upserts).
- **Every migration that creates a table in `public` must also `GRANT` on it in the same file.** Since 2026-10-30 Supabase no longer grants Data API access to new `public` tables automatically (existing tables kept their grants). Until then no migration here needed grants, so almost none have them — a new table without them fails in the client with `permission denied` on `supabase.from(...)`, even with correct RLS policies (RLS filters rows, the grant opens the table at all). Default: `grant select, insert, update, delete on public.x to authenticated;` plus the same `to service_role;`, and `grant select ... to anon` only if it must be readable without login. Tables touched solely by `SECURITY DEFINER` RPCs/triggers work without grants, but add them anyway so a later direct read doesn't break. Replaying all migrations into a fresh project (e.g. a new test project) would leave *every* table ungranted — that would need a one-off catch-up grant migration.
- **Every caller of `rebuild_elo()` must take `pg_advisory_xact_lock(hashtext('rebuild_ratings'))` first** (`trg_rebuild_ratings`, `admin_refresh_stats`, `nightly_refresh` since `supabase/2026-09-24d_serialize_rating_rebuild.sql`). `rebuild_elo()` empties and rewrites `ratings`; two transactions doing that at once collide on `ratings_pkey`, and the whole report/confirm/reject rolls back — 3 of 5 simultaneous reports failed in a stress test. A new function that calls `rebuild_elo()` without the lock brings this back. The lock turns collisions into waiting, and each rebuild takes ~1 s, so beyond ~8 simultaneous writes the tail hits Supabase's 8 s statement timeout; **every client call that writes `matches` therefore goes through `rpcRetry()` (`src/lib/rpcRetry.js`)**, which retries only transient DB errors (timeout, deadlock, lock, the old `ratings_pkey` collision) up to 4× with growing jittered pauses — safe because an aborted transaction is rolled back completely. Stress test: 15/15 simultaneous reports saved; the real ceiling (~20+ at once) is `rebuild_elo()`'s full recompute on every change.
- **MCP servers (including the Supabase one) load only at session start.** Running `claude mcp add` or authenticating a server mid-session does not make it available in that session — a brand-new chat is required.
- The 3-column desktop layout (narrow/wide/narrow) used across Übersicht/Live/Statistik/Profil is referred to internally as **"dünn-breit-dünn"**; `IdentityCard.jsx` is the shared component behind it, deliberately used instead of separate per-screen hero/profile variants.
- **Admin-created logins (`admin_create_user`/`admin_create_login`, see `supabase/2026-09-05_*.sql`) insert directly into `auth.users`/`auth.identities`** to skip Supabase's email-confirmation flow entirely (avoids the low default email-sending rate limit when onboarding many testers with disposable addresses on the test project). When inserting such a row, `confirmation_token`, `recovery_token`, `email_change_token_new`, and `email_change` **must** be set to `''`, never left `NULL` — GoTrue scans them into non-nullable Go strings and a `NULL` there produces a generic `"Database error querying schema"` (HTTP 500) on `signInWithPassword`, which looks nothing like an email/confirmation problem. Confirmed by live-testing against the actual Auth REST endpoint, not just by reading GoTrue's source.
- **Nichts, das den Login ueberleben muss, gehoert in `sessionStorage`** (siehe `src/lib/session.js`). `sessionStorage` gilt pro Tab, und der Magic-Link aus der Mail oeffnet praktisch immer einen neuen Tab oder gleich das In-App-Webview der Mail-App. Genau daran ist die Werbe-Zuordnung monatelang unbemerkt gescheitert: der Einladungscode aus `?ref=` lag im sessionStorage, war beim Registrieren weg, `register_player()` bekam `p_ref = null`, und weil ohne Code gar nichts vermerkt wird, sah die Datenbank hinterher aus wie "niemand wurde je geworben" (0 von 26 Spielern mit `invited_by`) statt nach einem Fehler. Seit 2026-09-21: `localStorage` mit 30-Tage-Ablauf, plus der Code haengt zusaetzlich an `emailRedirectTo` des Magic-Links, damit auch ein anderer Browser ihn noch mitbekommt. `?vs=` (Schnellmatch) liegt weiter im sessionStorage - das ist Absicht, es wird im selben Tab eingeloest.
- **Badge-Berechnung laeuft nur dort, wo sie jemand ausloest.** `compute_recruit_badges()` & Co. haengen an `confirm_match()` und dem Badge-Trigger, also an Matches. Ein Ereignis, das kein Match ist (z.B. eine Registrierung ueber einen Einladungscode), muss die passende compute-Funktion selbst aufrufen - sonst stimmt zwar die Datenlage, aber der Erfolg erscheint erst irgendwann spaeter beim naechsten Match. `register_player()` tut das seit 2026-09-21.
- **Re-numbering rows under a `UNIQUE(parent_id, position)` constraint in Postgres must never let two rows share a position "in transit" — and a NOT DEFERRABLE constraint checks this per row as it's written, not even at end-of-statement.** A first symptom hit in `winner_stays_report_game()` (`supabase/2026-09-09b_fix_winner_stays_rotation.sql`, 3 participants): a single bulk `UPDATE ... SET position = position - 1 WHERE position > N` failed with `duplicate key value` because the row that used to hold position `N` hadn't been moved out of the way first — patched by moving the vacating row to a sentinel value (`-1`) before shifting everyone else down. That patch turned out to be incomplete: with 4+ participants, the SAME bulk `UPDATE` can move *two or more* rows in one statement where row A's target position is row B's not-yet-processed source position — a "shift chain" — and Postgres may write them in an order that transiently collides, since a non-deferrable constraint is enforced as each row is written, not deferred to end-of-statement as originally assumed. The robust fix (`supabase/2026-09-10c_fix_winner_stays_constraint_deferrable.sql`) is `ALTER TABLE ... ALTER CONSTRAINT ... DEFERRABLE INITIALLY DEFERRED` — this checks the constraint once at transaction end, after every row already has its final, distinct value, making any reordering logic robust regardless of how many rows move in one call. Prefer a deferrable constraint over sentinel-value workarounds from the start for any future "reorder a ranked/queued list" table.

## Workflow

Work happens on the `test` branch; changes only go to `main` after the user explicitly asks for a merge. **Version numbers follow that split:** every push on `test` bumps `APP_VERSION` as `<last prod number>.<minor>` (e.g. `391.26`); when the user approves a merge, the merge commit on `main` sets the next WHOLE number (392, no minor) and `test` continues at `392.0`. Read the current prod number from `origin/main` (`git show origin/main:src/lib/constants.js`), not from a possibly stale local `main`. Name the new version in the reply to every push. SQL migration files are applied manually by the user (test project first, then prod) — Claude's Supabase access is read-only by design, so schema/data changes always go through a migration file for the user to run, never through direct execution.

**Realismus ist Pflicht und wird geprüft.** Ein Fall zeigt eine MÖGLICHE Situation im jeweiligen Spiel: ein Fall hat mehrere **Sätze** (`sets`: `discs`, `tag`, `variants`), je Disziplin die passenden Kugeln (8-Ball: eigene Gruppe Volle, Gegner Halbe; 9/10-Ball: die niedrigste Kugel steht im Etikett; 14/1: Ansage; Anstoß: das richtige Rack). `tag` erscheint als Chip über dem Tisch, die Disziplin-Kugeln neben dem Titel schalten zwischen den Sätzen um; `tagSets(variants, [[discs, tag], …])` in `meta.js` gibt denselben Varianten je Disziplin-Gruppe ein anderes Etikett. **Kugelkontakte folgen der Physik:** gleiche Rollreibung für alle (`FRICTION`), die getroffene Kugel startet mit dem Treffertempo, die Objektkugel läuft entlang der Mittelpunktslinie, die Weiße bei einem Schnitt tangential weiter (90°-Regel, Weglänge = Weg der Objektkugel · tan²φ). Dafür gibt es **`cut(from, {id, at}, objTo, opts)`** (Ziel der Objektkugel vorgeben), `cutAngle()` (Winkel vorgeben) und `bankPoint()` (Stoß über die Bande); eine Weiße, die bei Winkel einfach stehen bleibt, ist ein Fehler (`stop: true` nur für bewusste Halte wie Doppeltreffer oder Break). Neu seit 2026-10-06: Kugeln können mit `hidden: true` beginnen und per `place: true` hingelegt werden (Neuaufbau, Ball in Hand), Tischlinien per `table: {headLine, triangle}` (Kopflinie/Kopffeld, Fuß-/Kopf-/Mittelpunkt, Dreieck), Urteilstext per `verdictLabel`, Sprechblase per `say`.

**Zwei Prüfskripte, beide vor jedem Fall-Commit laufen lassen:** `node scripts/checkRules.mjs` (Pflichtfelder, `discs` ↔ Sätze, englische Übersetzungen vollständig und konsistent über alle Fälle, keine doppelten Schlüssel, Kugeln auf dem Tisch und nie übereinander, **keine Kollision während der Bewegung**, Objektkugel auf der Mittelpunktslinie, Weiße setzt nach Schnitt fort) und `node scripts/checkSearch.mjs` (~130 echte Suchanfragen deutsch/englisch: Wort, Frage, Tippfehler, Umlaute, Regelnummer, „nichts finden“ für noch nicht vorhandene Regeln; neue Fälle bekommen hier ihre Anfragen). **Die Suche** (`search.js`) normalisiert (ß/ä/ö/ü, „9 Ball“ → 9ball, „14.1“/„Straight Pool“ → 14/1, „Ball in Hand“, „Push-Out“), entfernt Füllwörter, gewichtet Felder (Name 6, Suchbegriffe 5, Regelnummer 5, Thema/Disziplin/Etikett 3, Text 1), toleriert einen Tippfehler ab 5 Zeichen, kennt Synonyme (`SYN_RAW`) und verlangt UND; ein ODER-Auffangnetz gibt es nur bei ≥ 3 Wörtern, sonst lieber „nichts gefunden“ als etwas Irreführendes. Kein Lookbehind in Regexen (ältere iPhones). **Neuer Fall = neue Datei in `cases/` (Etikett/Kugeln je Disziplin beachten) + Anfragen in `checkSearch.mjs`, sonst nichts.** `released: false` ist der Haken für die spätere Freigabe. Offen: Regeln, die gezeichnete Queue/Hand/Fuß brauchen (Durchstoß, Schieben, Fuß am Boden, Kugel berühren), siehe Regelliste.
